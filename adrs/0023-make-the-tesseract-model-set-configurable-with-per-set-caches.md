# Make the Tesseract model set configurable with per-set caches

## Context and Problem Statement

Tesseract publishes two model sets for the same 126 languages, both
Apache-2.0: `tessdata_fast` (integer LSTM, 362 MB in all) and `tessdata_best`
(float LSTM, 1.15 GB in all, the largest file 15.1 MiB). xberg downloaded only
`tessdata_fast`, into a flat `<cache>/tessdata`, and searched system tessdata
directories, which hold `tessdata_fast` too. `best` may read some documents
better at a higher cost, and which one should be the default is not settled.
How should xberg offer both without one request mixing sets, without results
depending on what happens to be cached or installed, and with the default
left to a measurement?

## Decision Drivers

* A request for one set is never served the other set's files.
* Every download is pinned and hash-verified.
* Existing caches and installs keep working for `fast` without a re-download.
* Changing the default later is a one-line change on native targets and does
  not move WebAssembly or mobile.
* OCR results cached for one set are never returned for the other.

## Considered Options

* A model-set option with a cache directory per set.
* A model-set option sharing the flat cache, keyed by file name suffix.
* No option: users point `tessdata_path` or `TESSDATA_PREFIX` at `best` data.

## Decision Outcome

Chosen option: "A model-set option with a cache directory per set", because
directory identity alone then keeps the sets apart in every resolver, probe
and cache key that already works per directory.

`OcrConfig.tessdata_model` (`"fast"` or `"best"`; environment
`XBERG_OCR_TESSDATA_MODEL`; CLI `--ocr-tessdata-model`) selects the set. The
name sits beside `tessdata_path` and `tessdata_bytes`, and the values are the
upstream repository suffixes. Resolution takes the first directory holding
every requested language:

1. `tessdata_path`, then `TESSDATA_PREFIX`, used as given for either set.
2. `<cache>/tessdata/<set>`.
3. For `fast` only: the flat `<cache>/tessdata` older releases filled, then
   the system directories. Both hold `tessdata_fast`, so they never satisfy
   `best`.
4. Otherwise the missing packs are downloaded into `<cache>/tessdata/<set>`
   from one pinned revision per set (`tessdata_fast` 8741641, `tessdata_best`
   e12c65a) and checked against SHA-256 pins generated by
   `scripts/generate_tessdata_pins.py`. For `fast`, a flat-cache pack that
   matches its pin is linked or copied in instead of downloaded, and `eng` can
   come from the bundled model.

`osd` and `equ` are byte-identical in both sets; each set still keeps its own
copy so the directories stay independent. `frk` is fetched from `deu_latf` in
both sets: upstream keeps it only as a symlink in `tessdata_fast` and dropped
it from `tessdata_best`.

The set is hashed into the OCR result cache key next to the resolved
directory, and into the language-probe memo key. The default is
`DEFAULT_TESSDATA_MODEL`, `fast`, defined separately for native targets and
for WebAssembly, Android and iOS; WebAssembly also asserts at compile time that
its default is `fast`. The WebAssembly backend bundles only `tessdata_fast`
English (a bundled `best` English model would put the module at about 54.7 MB,
over the 51,380,224-byte publish limit and jsDelivr's 52,428,800-byte cap) and
rejects `best` unless the caller supplies the bytes in `tessdata_bytes`.

Whether native builds default to `best` is decided by an OCR quality and
latency measurement, not by this record.

### Consequences

* Good, because a `best` request reads only `best` files or the caller's own
  directory, so its output does not depend on cache history.
* Good, because `fast` keeps today's search order and existing caches.
* Good, because `xberg cache warm --tessdata-model` and
  `--tessdata-languages` prefetch either set for offline hosts.
* Bad, because `best` cannot use the system packages and downloads 3-4 times
  as many bytes per language on first use.
* Bad, because new `fast` downloads land in `tessdata/fast` while the flat
  directory stays, so an upgraded cache can hold a pack twice (hard-linked
  where the file system allows).
* Bad, because every existing OCR result cache entry misses once after the
  key change.

### Confirmation

Unit tests cover config, environment and CLI parsing, the per-set search
order (`test_best_search_dirs_hold_no_fast_only_directory`,
`test_best_request_never_resolves_to_a_fast_only_directory`), override and
`TESSDATA_PREFIX` precedence, cache keys per set, both pin tables, and the
WebAssembly refusal of `best` without caller bytes. The pin generator
reproduces the committed `tessdata_fast` table byte for byte and checks every
download against the Git blob size and SHA-1 of the pinned tree.

To switch native builds to `best`: change the native `DEFAULT_TESSDATA_MODEL`,
the `OcrConfig.tessdata_model` documentation and the OCR guide; decide whether
`scripts/lib/tessdata.sh`, `ensure-tesseract-windows.ps1` and the Docker
images provision `best` packs (into `tessdata/best` or through
`TESSDATA_PREFIX`), since system packages then stop counting; re-check tests
that rely on the flat cache through the default set; and leave
`bundle-tessdata-eng`, the notices and WebAssembly unchanged.

## Pros and Cons of the Options

### A model-set option with a cache directory per set

* Good, because directory identity alone separates the sets, so every
  existing resolver, probe and fingerprint keeps working per directory.
* Bad, because the default set needs a migration path from the flat cache.

### A model-set option sharing the flat cache

* Good, because no new directories.
* Bad, because Tesseract loads `<lang>.traineddata` by name, so a suffix
  scheme needs a renamed copy or a per-request staging directory.

### No option

* Good, because nothing changes.
* Bad, because `best` then needs hand-provisioned, unverified files, and a
  partially provisioned directory silently falls back to `fast` packs
  elsewhere in the chain.
